# DDD 이해

## 단어 뜻

- `DDD`: Domain-Driven Design의 줄임말입니다. 서비스를 움직이는 업무 규칙과 현업의 말을 중심에 두고 소프트웨어를 설계하는 방식입니다.
- `도메인`: 개발자가 해결하려는 업무 영역입니다. 예를 들어 주문, 결제, 배송, 정산처럼 서비스가 실제로 다루는 문제 영역을 말합니다.
- `모델`: 도메인을 코드로 다루기 위해 만든 핵심 개념의 묶음입니다. 단순한 데이터 모양이 아니라 업무 규칙과 행동까지 포함합니다.
- `유비쿼터스 언어`: 기획자, 현업, 개발자가 같은 뜻으로 쓰기로 맞춘 공통 언어입니다.

## 예시 스토리

온라인 쇼핑몰에서 "주문 취소" 기능을 만든다고 해봅니다.
처음에는 버튼을 누르면 주문 상태만 `취소`로 바꾸면 된다고 생각했습니다.
그런데 상담팀은 결제 취소를 말하고, 물류팀은 출고 중단을 말하고, 정산팀은 매출 제외를 말하고 있었습니다.
같은 "취소"라는 말이 팀마다 다른 의미였던 것입니다.
DDD는 이런 상황에서 먼저 업무의 말과 규칙을 맞추고, 그 규칙이 코드 안에서도 흐트러지지 않게 설계하려는 접근입니다.

## 한 줄 요약

DDD는 데이터베이스나 화면부터 정하는 대신, 서비스의 업무 규칙과 공통 언어를 코드의 중심에 두는 설계 방식입니다.

## 개념 설명

DDD의 핵심은 "코드 구조를 어떻게 나눌까?"보다 "이 서비스가 실제로 해결하는 문제가 무엇인가?"를 먼저 묻는 데 있습니다.
업무에서 중요한 개념을 찾고, 그 개념이 어떤 규칙으로 움직이는지 정리한 뒤, 그 규칙을 코드 모델에 반영합니다.

예를 들어 주문 도메인에서는 `Order`가 단순히 주문 테이블 한 줄이 아닐 수 있습니다.
주문은 결제 여부, 출고 상태, 취소 가능 시간, 쿠폰 복구 여부 같은 규칙을 함께 가집니다.
DDD에서는 이런 규칙이 여러 서비스 함수나 컨트롤러에 흩어지지 않도록 도메인 모델 가까이에 둡니다.

DDD에서 자주 나오는 개념은 다음과 같습니다.

- `Bounded Context`: 같은 단어가 같은 뜻으로 쓰이는 경계입니다. "고객"이 주문팀에서는 구매자이고, 상담팀에서는 문의자일 수 있다면 문맥을 나눠야 합니다.
- `Entity`: 식별자가 중요하고 시간이 지나도 같은 대상으로 추적되는 객체입니다. 주문 번호가 있는 주문이 대표적입니다.
- `Value Object`: 식별자보다 값 자체가 중요한 객체입니다. 금액, 기간, 주소처럼 값이 같으면 같은 의미로 보는 경우입니다.
- `Aggregate`: 함께 일관성을 지켜야 하는 도메인 객체 묶음입니다. 외부에서는 보통 Aggregate Root를 통해서만 변경합니다.
- `Repository`: 도메인 모델을 저장하고 다시 가져오는 역할입니다. 도메인 규칙을 데이터 접근 코드에 섞지 않기 위해 사용합니다.
- `Domain Service`: 특정 Entity나 Value Object 하나에 넣기 어려운 도메인 규칙을 표현할 때 사용합니다.

DDD는 폴더 이름을 `domain`, `application`, `infrastructure`로 나눈다고 자동으로 적용되는 것이 아닙니다.
반대로 폴더 구조가 단순해도, 팀이 같은 언어로 업무 규칙을 정리하고 그 규칙이 코드에 잘 드러난다면 DDD의 중요한 부분을 쓰고 있는 것입니다.

## 언제 쓰면 좋은가

- 업무 규칙이 복잡하고 예외가 자주 생길 때 좋습니다.
- 기획, 운영, 개발이 같은 단어를 다르게 써서 오해가 반복될 때 좋습니다.
- 여러 팀이 같은 서비스를 나눠 만들고, 경계를 명확히 잡아야 할 때 좋습니다.
- 단순 CRUD 관리자 화면처럼 규칙이 거의 없는 기능에는 과할 수 있습니다.

## 자주 하는 실수

- DDD를 레이어드 아키텍처나 폴더 구조로만 이해합니다.
- 모든 클래스를 Entity나 Value Object로 만들려고 합니다.
- 실제 업무 언어를 맞추지 않은 채 코드 패턴만 먼저 적용합니다.
- 도메인 규칙을 컨트롤러, SQL, 화면 로직에 흩어 놓고 모델은 데이터 주머니처럼 둡니다.

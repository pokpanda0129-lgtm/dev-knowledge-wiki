# 카나리 배포

## 단어 뜻

- `Canary`: 원래는 위험을 먼저 감지하기 위해 쓰던 작은 새를 뜻합니다. 배포에서는 새 버전을 전체 사용자에게 바로 열지 않고, 일부 사용자에게 먼저 열어 보는 방식을 말합니다.
- `배포`: 새 코드나 설정을 실제 서비스 환경에 반영하는 일입니다.
- `트래픽`: 서비스로 들어오는 요청의 흐름입니다. 사용자 접속, API 호출, 페이지 이동 요청이 모두 트래픽이 될 수 있습니다.
- `롤백`: 문제가 생겼을 때 이전 버전으로 되돌리는 일입니다.

## 예시 스토리

카페에서 새 메뉴를 출시한다고 해봅니다.
처음부터 모든 매장에 새 메뉴를 팔기보다, 몇몇 매장에서 먼저 팔아 보고 주문 속도, 손님 반응, 재료 부족 문제를 확인합니다.
문제가 없으면 점점 더 많은 매장으로 늘리고, 문제가 있으면 작은 범위에서만 멈추면 됩니다.
카나리 배포도 이와 비슷하게 새 버전을 일부 요청에만 먼저 적용해 운영 위험을 작게 나눕니다.

## 한 줄 요약

카나리 배포는 새 버전을 전체에 한 번에 배포하지 않고, 일부 사용자나 일부 서버에 먼저 열어 보면서 문제를 확인한 뒤 점진적으로 넓히는 배포 방식입니다.

## 개념 설명

카나리 배포의 핵심은 "새 버전을 작게 노출하고, 지표를 보며 범위를 넓히는 것"입니다.
예를 들어 전체 요청의 5%만 새 버전으로 보내고, 오류율과 응답 시간, 주문 실패율 같은 지표를 확인합니다.
문제가 없으면 10%, 30%, 50%, 100%처럼 비율을 늘립니다.
문제가 보이면 새 버전으로 가는 트래픽을 줄이거나 이전 버전으로 되돌립니다.

카나리 배포는 보통 로드 밸런서, API 게이트웨이, 서비스 메시, 쿠버네티스, 배포 플랫폼 같은 인프라에서 트래픽 비율을 조절해 구현합니다.
구성에 따라 특정 사용자 그룹, 특정 지역, 내부 직원, 일부 서버 인스턴스만 새 버전을 보게 할 수도 있습니다.
중요한 점은 배포 자체보다 관찰 기준입니다.
어떤 오류율이면 멈출지, 어떤 지표가 정상인지, 문제가 생기면 누가 어떻게 롤백할지를 미리 정해야 카나리 배포가 의미가 있습니다.

카나리 배포는 기능 플래그와 함께 쓰이는 경우도 많습니다.
카나리 배포가 "어떤 버전의 서버로 요청을 보낼지"를 조절한다면, 기능 플래그는 "같은 버전 안에서 어떤 기능을 켤지"를 조절하는 데 가깝습니다.
둘은 서로 대체 관계라기보다 함께 쓰면 더 세밀하게 위험을 줄일 수 있는 도구입니다.

## 언제 쓰면 좋은가

- 결제, 주문, 로그인처럼 장애 영향이 큰 기능을 배포할 때 좋습니다.
- 실제 운영 트래픽에서만 드러나는 성능 문제나 예외를 확인해야 할 때 좋습니다.
- 한 번에 전체 롤백하기 부담스러운 큰 변경을 점진적으로 풀고 싶을 때 좋습니다.
- 사용자가 거의 없거나 장애 영향이 작은 내부 도구에는 과할 수 있습니다.

## 자주 하는 실수

- 카나리 비율만 나누고 오류율, 지연 시간, 비즈니스 지표를 보지 않습니다.
- 새 버전과 이전 버전이 같은 데이터베이스를 쓰는데, 스키마 변경 호환성을 확인하지 않습니다.
- 문제가 생겼을 때 트래픽을 되돌리는 방법은 있지만 데이터 변경을 되돌릴 방법은 준비하지 않습니다.
- 캐시, 세션, 메시지 큐처럼 요청 경로 밖의 공유 자원을 고려하지 않습니다.
- 일부 사용자에게만 보인 문제라고 가볍게 보고, 실제 전체 배포 전에 원인을 확인하지 않습니다.

# 정확성 검증 기준

개발 지식 위키 문서는 이해하기 쉬워야 하지만, 쉬운 비유 때문에 기술적으로 틀리면 안 됩니다.

## 공통 기준

- 비유는 개념 이해를 돕는 용도로만 사용합니다.
- 비유가 기술적 사실을 왜곡하면 반드시 보완 문장을 붙입니다.
- 이야기는 재미보다 정확성이 우선입니다. 웃기거나 기억에 남는 장면을 쓰더라도 실제 개념의 조건과 예외를 흐리면 안 됩니다.
- 이야기에는 예상이 깨지는 사건이 있어도 좋지만, 그 사건이 개념의 핵심 차이와 직접 연결되어야 합니다.
- 비교형 문서에서 여러 개념을 비유할 때는 같은 세계관이나 같은 축의 예시로 상반되게 설명합니다.
- 이미지를 별도로 만들었다면 비교 이미지는 같은 구도와 같은 시각 문법으로 그립니다. 차이를 보여주려면 배치 전체를 바꾸지 말고, 전달되는 물체나 완성 위치처럼 핵심 차이만 바꿉니다.
- 이미지를 별도로 만들었다면 이미지 라벨은 문서의 비유 단어와 맞춥니다. 설명에서 쓴 단어를 이미지에서 다른 기술 용어로 바꾸면 독자가 다른 개념으로 오해할 수 있습니다.
- `항상`, `무조건`, `완성`, `불가능`, `절대` 같은 단정 표현은 조심합니다.
- 예외가 중요한 개념이면 "대부분", "보통", "경우가 많다", "구성에 따라 다르다"처럼 범위를 밝힙니다.
- 최신 프레임워크 동작, 배포 방식, 캐시 정책처럼 환경별 차이가 큰 내용은 특정 조건을 함께 씁니다.

## 렌더링 개념 검증

- SSR은 HTML을 먼저 받는 것이지, JavaScript 상호작용까지 완전히 끝난 상태가 아닙니다.
- SSR 설명에는 hydration이 필요한 경우를 확인합니다.
- CSR 설명에는 JavaScript 실행, API 호출, 초기 로딩 상태를 확인합니다.
- SPA 설명에는 첫 진입과 라우터 이동을 구분합니다.
- SPA와 CSR, MPA와 SSR을 같은 말처럼 쓰지 않습니다.
- 같은 Nuxt 앱도 첫 진입은 SSR, 이후 이동은 SPA처럼 동작할 수 있음을 확인합니다.

## 인프라와 캐시 검증

- Browser, OpenResty, Nuxt/Nitro, WAS의 책임을 섞어 쓰지 않습니다.
- Nitro가 WAS를 완전히 대체한다고 표현하지 않습니다.
- 캐시는 위치, 키, TTL, 무효화 순서를 함께 설명합니다.
- 공유 캐시에 사용자별 응답이 저장될 수 있는 표현은 피합니다.
- 캐시 삭제 명령어는 복사 즉시 운영 데이터가 삭제되지 않게 작성합니다.

## 리뷰 질문

문서 작성 후 아래 질문에 답합니다.

- 이 비유가 기술적으로 틀린 오해를 만들지 않는가?
- 초보자가 이 문장만 외웠을 때 실무에서 틀린 판단을 하지 않는가?
- 첫 진입과 이후 동작이 다른 개념을 하나로 뭉개지 않았는가?
- 환경이나 설정에 따라 달라지는 내용을 단정하지 않았는가?
- 운영 명령어가 복사 즉시 위험하게 실행되지 않는가?

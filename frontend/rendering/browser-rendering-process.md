# 브라우저 렌더링 원리

## 단어 뜻

- `렌더링`: HTML, CSS, JavaScript를 브라우저가 해석해서 화면에 픽셀로 보여주는 과정입니다.
- `DOM`: HTML을 브라우저가 이해할 수 있는 노드 구조로 바꾼 것입니다.
- `CSSOM`: CSS를 브라우저가 이해할 수 있는 스타일 규칙 구조로 바꾼 것입니다.
- `Render Tree`: 화면에 실제로 그릴 요소와 스타일만 모아둔 구조입니다.
- `Layout`: 각 요소가 화면의 어디에, 어떤 크기로 놓일지 계산하는 단계입니다.
- `Paint`: 글자, 색, 테두리, 그림자 같은 시각 정보를 그리는 단계입니다.
- `Composite`: 여러 그려진 층을 합쳐 최종 화면으로 보여주는 단계입니다.

## 예시 스토리

행사장에 무대를 설치한다고 생각해봅니다. 먼저 진행표를 보고 의자, 단상, 안내판 같은 필요한 물건 목록을 만듭니다. 그다음 디자인 지침서를 보고 각 물건의 색, 크기, 위치 규칙을 붙입니다. 그런데 중간에 담당자가 와서 “단상 위치를 바꿔주세요”라고 하면, 설치팀은 이미 놓은 물건의 위치를 다시 계산하고 일부를 다시 칠해야 합니다. 브라우저 렌더링도 이처럼 문서를 읽고, 스타일을 입히고, 위치를 계산하고, 화면에 그리는 일을 순서대로 처리합니다.

## 한 줄 요약

브라우저 렌더링은 받은 HTML과 CSS를 구조로 바꾸고, 어떤 요소를 어디에 그릴지 계산한 뒤, 실제 화면 픽셀로 보여주는 과정입니다.

## 개념 설명

브라우저는 HTML을 받으면 위에서 아래로 읽으면서 DOM을 만듭니다. CSS 파일이나 `<style>`을 만나면 CSSOM도 만듭니다. DOM은 “무엇이 있는지”를 나타내고, CSSOM은 “어떻게 보여야 하는지”를 나타냅니다.

DOM과 CSSOM이 준비되면 브라우저는 실제 화면에 필요한 요소만 골라 Render Tree를 만듭니다. 예를 들어 `display: none`인 요소는 DOM에는 있어도 화면에는 그리지 않으므로 Render Tree에서 빠집니다.

그다음 Layout 단계에서 요소의 크기와 위치를 계산합니다. “이 버튼은 몇 px 너비인지”, “이 문단은 몇 번째 줄에서 줄바꿈되는지”, “부모 박스 안에서 어디에 놓이는지”를 정합니다.

위치가 정해지면 Paint 단계에서 색, 글자, 이미지, 테두리, 그림자를 그립니다. 마지막으로 Composite 단계에서 여러 layer를 합쳐 사용자가 보는 최종 화면을 만듭니다.

JavaScript는 이 흐름에 끼어들 수 있습니다. JavaScript가 DOM을 추가하거나 class를 바꾸면 브라우저는 일부 단계를 다시 해야 할 수 있습니다. 위치와 크기가 바뀌면 Layout을 다시 계산해야 하고, 색만 바뀌면 Paint만 다시 하면 되는 경우도 있습니다.

그래서 실무에서는 DOM을 너무 자주 바꾸거나, 크기 계산을 반복해서 읽고 쓰는 코드를 조심합니다. 작은 변경처럼 보여도 브라우저 입장에서는 위치 재계산과 다시 그리기가 반복되어 화면이 버벅일 수 있습니다.

## 그래서 뭐가 좋은데?

- 화면이 느리게 뜰 때: HTML/CSS/JS 중 어느 단계가 막고 있는지 나눠서 볼 수 있습니다.
- 애니메이션이 버벅일 때: Layout을 자주 다시 만들고 있는지, Paint가 큰지 의심할 수 있습니다.
- CSS를 수정할 때: 위치를 바꾸는 속성과 색만 바꾸는 속성의 비용이 다를 수 있음을 이해할 수 있습니다.
- CSR/SSR을 볼 때: HTML을 언제 받느냐뿐 아니라, 받은 뒤 브라우저가 화면으로 만드는 과정까지 함께 생각할 수 있습니다.

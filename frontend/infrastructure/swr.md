# SWR

## 단어 뜻

- `SWR`: `stale-while-revalidate`의 줄임말입니다. 오래된 캐시를 잠깐 보여주면서, 뒤에서는 새 데이터를 다시 확인하는 방식입니다.
- `stale`: 캐시 유효 시간이 지나서 최신이라고 장담할 수 없는 상태입니다.
- `revalidate`: 원본 서버에 다시 확인해서 캐시가 아직 맞는지, 새로 받아야 하는지 검사하는 일입니다.
- `max-age`: 캐시를 신선하다고 볼 수 있는 시간입니다.

## 예시 스토리

분식집 앞에 오늘의 메뉴판이 걸려 있습니다. 점심시간이 지나 메뉴판이 조금 오래됐지만, 손님이 몰려오면 직원은 일단 그 메뉴판을 보여주고 주문 줄이 멈추지 않게 합니다. 동시에 다른 직원이 주방에 뛰어가서 가격이나 품절 메뉴가 바뀌었는지 확인합니다. 확인 결과가 돌아오면 입구 메뉴판을 새것으로 갈아 끼우고, 다음 손님부터는 갱신된 메뉴판을 봅니다.

## 한 줄 요약

SWR은 "조금 오래됐을 수 있는 캐시를 먼저 보여주고, 새 데이터 확인은 뒤에서 진행하는" 캐시 전략입니다.

## 개념 설명

일반적인 캐시는 유효 시간이 끝나면 다음 요청이 원본 서버의 응답을 기다려야 합니다. 그래서 캐시가 만료된 순간에 사용자는 느린 응답을 경험할 수 있습니다.

SWR은 이 대기 시간을 줄이기 위한 방식입니다. 캐시가 `max-age` 안에 있으면 그대로 신선한 응답으로 사용합니다. `max-age`는 지났지만 `stale-while-revalidate` 시간 안에 있으면, 캐시는 오래된 응답을 먼저 돌려주고 뒤에서 원본 서버에 다시 확인합니다. 새 응답이 있으면 캐시를 갱신하고, 그대로라면 기존 캐시를 유지한 뒤 다음 요청에도 사용합니다.

예를 들어 다음 헤더는 60초 동안은 신선한 캐시로 쓰고, 그 뒤 300초 동안은 오래된 캐시를 먼저 보여주면서 뒤에서 갱신할 수 있다는 뜻입니다.

```http
Cache-Control: public, max-age=60, stale-while-revalidate=300
```

SWR은 뉴스 목록, 상품 목록, 공지 목록처럼 "아주 잠깐 오래된 내용이 보여도 괜찮지만 응답 속도가 중요한 화면"에 잘 맞습니다. 반대로 재고 차감, 결제 상태, 권한 확인처럼 틀리면 바로 문제가 되는 응답에는 조심해야 합니다. 특히 사용자별 응답을 공유 캐시에 섞으면 다른 사용자의 정보가 보일 수 있으므로 캐시 키와 공개 범위를 반드시 분리해야 합니다.

프론트엔드에서 말하는 `SWR` 라이브러리는 이 아이디어를 데이터 패칭에 적용한 도구에 가깝습니다. HTTP 캐시의 `stale-while-revalidate`는 브라우저, CDN, 프록시 같은 캐시 계층에서 쓰는 정책이고, 라이브러리의 SWR은 화면 안에서 "캐시된 데이터를 먼저 보여주고 뒤에서 다시 요청한다"는 패턴을 구현합니다.

## 그래서 뭐가 좋은데?

- 빠른 응답이 중요하고 몇 초 전 데이터가 허용되는 화면: SWR이 잘 맞습니다.
- 항상 최신 상태가 먼저 보여야 하는 화면: SWR보다 즉시 재검증하거나 캐시하지 않는 쪽이 안전합니다.
- CDN이나 OpenResty 같은 앞단 캐시를 쓰는 구조: SWR을 쓰면 원본 서버 부하를 줄이면서 만료 순간의 느린 응답을 줄일 수 있습니다.
- 사용자별 데이터가 섞이는 API: 공유 SWR 캐시를 쓰기 전에 `private`, `Vary`, 쿠키, 인증 헤더, 캐시 키를 먼저 확인해야 합니다.
